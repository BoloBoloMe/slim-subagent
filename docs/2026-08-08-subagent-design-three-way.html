subagents, three recipes

同一味药, 三种配方
Claude Code, Codex 与 pi-subagents 的子代理设计

两个商业旗舰 (Claude Code, Codex) 和一个开源社区插件 (pi-subagents, 跑在 pi 上) 交出了各自的 subagent 答卷. 诊断相同, 处方却很有意思地不同. 这一页只谈产品设计 — 功能如何被呈现, 触发, 约束与沉淀 — 不碰实现细节. 信息来自三方官方文档/仓库 (2026 年中版本), 出处见文末.

1同一个敌人: 上下文噪声, 与轻信

本节目标: 说明 subagent 不是新能力, 而是对同一个老问题的回答 — 三家对「老问题是什么」的表述本身就有信息量.

两家商业产品的文档用几乎相同的语言描述病因. Claude Code 说: 搜索记录, 日志, 文件内容会 「flood your main conversation」; Codex 更干脆, 直接引用术语 上下文污染 (context pollution, 有用信息被中间输出淹没) 和 上下文腐烂 (context rot, 窗口越满, 表现越差).

pi-subagents 的 README 几乎不谈上下文, 它说卖点是 「a second or third set of model eyes」— 第二双, 第三双眼睛. 同一味药, 商业产品主治噪声, 这个插件还治轻信: 单个模型会一本正经地犯错, 换一个脑子 (甚至换一家厂商的模型) 再看一遍, 病就藏不住了.

于是共同的处方是: 主上下文是整个系统里最贵的资产, noisy 的体力活必须外包 — 子代理在自己的上下文窗口里翻垃圾, 只把摘要带回主线.

key idea · 上下文卫生 子代理存在的理由不是「更聪明」, 而是「更干净」. 它在独立窗口里干活, 主线只见摘要. 这是 subagent 的第一性原理 — 只不过 pi-subagents 在旁边补了一刀: 干净之外, 还要「被质疑过」.

2共同骨架: 已经收敛的部分

本节目标: 先列出三家不约而同的决策, 后面的分歧才衬得出来.

在骨架之上, 三家还有一串不约而同的产品决策:

  • 内置最小角色集: 一个读 (探索), 一个写 (执行), 一个审查/兜底. Claude Code 是 Explore / general-purpose / Plan; Codex 是 explorer / worker / default; pi-subagents 是 scout / worker / reviewer — 还多给一个「问」: oracle, 专职挑战决策本身.
  • 文件即定义: 自定义子代理都是「一个文件 = 一个 agent」, 都分项目级与个人级, 都鼓励项目级入库共享. Claude Code 与 pi-subagents 同宗 (Markdown + YAML frontmatter), Codex 用 TOML 配置层.
  • 权限默认继承, 可按 agent 收紧: 子代理继承父会话的权限上下文; 三家都支持把某个 agent 钉成只读/窄工具.
  • 模型与算力按角色分配: 探索用便宜快速的模型, 审查用高档推理 — 三份文档给了几乎相同的建议; pi-subagents 额外支持跨厂商 fallback (主模型挂了自动换别家).
  • 明示成本: 两家商业文档都警告: 每个子代理独立消耗模型与工具调用, token 账单高于单线程.
observation 行业已经收敛出「读」与「写」的最小分工: 读的并行是免费午餐, 写的并行是麻烦的开始. pi-subagents 多走了一步: 把「质疑」也做成内置角色 (oracle) — 这预告了它后面的路线.

3四个真正的分歧

本节目标: 前三个分歧三家同台, 第四个分歧是插件独自开辟的战场.

视角:

3.1 谁来决定 spawn: 模型路由 vs 显式请求 vs 显式意图 + 模型编排

Claude Code 自动委派是一等设计

  • 模型根据 description + 当前任务 + 上下文自动决定委派; 在 description 里写 “use proactively” 可鼓励主动分派.
  • description 本质上是写给模型的路由信号 — 一份招聘启事, 模型是招聘官.
  • 显式通道是兜底, 且分三级: 自然语言点名 → @-mention 强制运行 → --agent 让整个会话扮演该 agent.

Codex 显式触发是一等设计

  • 文档原话: 「Codex only spawns subagents when you explicitly ask it to」 — 直接要求, 或 AGENTS.md / skill 指令里写明委派.
  • description 被官方定义为 human-facing guidance — 写给人看的门牌, 不是路由信号.
  • 设计逻辑: 分工是资源决策 (token 成倍消耗), 决定权留在人和仓库指令里, 不交给模型即兴.

pi-subagents 意图在人, 编排在模型

  • 用户用自然语言点名意图 (「Use reviewer to review this diff」), 但是否调用工具, 选哪个 agent, 怎么组合 — 由 Pi 决定.
  • README 第一句就划线: 装插件 ≠ 后台自动 reviewer, 它只是给了 Pi 一把委派的工具; 想每次都审查, 得在指令里写明.
  • 位置介于两家之间: 意图显式 (像 Codex), 组合自主 (像 Claude Code).
nuance · 同一个字段, 三种读者 Claude Code 的 description 喂给模型当路由信号; Codex 的 description 写给人当门牌; pi-subagents 的 description 既给模型选 agent 用, 也允许你在设置里覆写它 — 人随时可以改招聘启事.

3.2 子代理是什么: 资产 vs 线程 vs 可编程的编排原语

Claude Code 资产: 定义被精心设计, 可以积累

子代理是 Markdown + YAML frontmatter 的资产文件, 五层来源带优先级, 可进版本控制, 可打包成 plugin 分发. 字段已成体系:

# .claude/agents/code-reviewer.md
---
name: code-reviewer
description: 代码审查专家. use proactively after edits.
tools: Read, Grep, Glob, Bash   # 工具白名单
model: sonnet                   # 按角色配算力
permissionMode: default
memory: project                 # 跨会话持久记忆
isolation: worktree             # 独立 repo 副本
---
你是资深 reviewer, 先给结论, 按严重度排序…
  • 还有 hooks, skills 预载, mcpServers, maxTurns, background 等字段; 定义甚至可被「agent teams」的队友复用.
  • 子代理只拿到自己的 system prompt + 基本环境信息, 看不到父对话全文 — 卫生靠结构保证.
  • 近期版本子代理默认后台运行, 可恢复, 可追加指令.

Codex 线程: 运行被精心设计, 用完即收

子代理的运行实体是 agent thread, 一等 UI 对象: 桌面端 / CLI / IDE 里可打开检视, 可中途 steer, 可停止, 可关闭; 编排 (spawn, 路由后续指令, 等全部结果, 关线程) 由 Codex 托管.

# .codex/agents/reviewer.toml
name = "reviewer"
description = "PR reviewer, correctness & security."
model = "gpt-5.6-terra"
model_reasoning_effort = "high"
sandbox_mode = "read-only"
developer_instructions = """
Lead with concrete findings.
Avoid style-only comments.
"""
  • TOML 的本质是「spawn 出来的会话的配置层」: 除了 name/description/developer_instructions, 可以直接覆盖任何会话配置 (模型, 沙箱, MCP, skills).
  • 官方自承: 这「can feel heavier than a dedicated agent manifest, and the format may evolve」— 定义格式尚未定型.
  • 不指定模型时, Codex 按任务自动平衡智能/速度/价格.

pi-subagents 原语: 组合本身是一等产品

子代理是完整的 pi 子会话, 而组合方式是一等概念: chain, parallel, async, fork/fresh 上下文, 可保存的工作流, 定时调度, mission 持久记录 — 甚至直接暴露一段 JS 让你编程编排:

subagent({ workflowScript: `
  const s = await runs.run("scan",
    { agent: "scout", task: "Scan the codebase" });
  return await runs.all([
    { key: "correct", agent: "reviewer",
      task: "Review: " + s.output },
    { key: "tests", agent: "reviewer",
      task: "Tests: " + s.output },
  ]);
` })
  • 可观测性长在 TUI 里: 常驻 FleetView 面板 + /subagents-fleet 检视器 (读 transcript, steer, stop) — 与 Codex 的线程检视异曲同工.
  • 自定义 agent 与 Claude Code 同宗 (Markdown frontmatter, 四层 scope: builtin < package < user < project), 另有 eject/disable/reset 等管理动作, 把内置 agent 拷出来改.
  • 套路被固化成 prompt 快捷方式: /parallel-review, /review-loop (审查-修复循环直到干净).
summary · 复杂度花在了三个不同的地方 Claude Code 把设计预算花在「定义」上 — 十几种字段, 五层作用域, 记忆与 hooks; Codex 花在「运行」上 — 线程的检视, 干预与生命周期; pi-subagents 花在「组合」上 — 链, 并行, 脚本, 调度, 快捷方式.

3.3 并行写的冲突: 工程解 vs 纪律解 vs 全都要

Claude Code 把冲突关进机制

  • isolation: worktree 给子代理一份独立的 git 工作区副本, 并行写互不相踩.
  • 子代理的命令若试图落回主 checkout, 直接报错 — 隔离由工具强制执行, 不靠自觉.

Codex 把冲突交给约定

  • 官方建议原文: 读密集任务 (探索, 测试, 分诊, 摘要) 放心并行; 写密集并行「be more careful」— 冲突与协调开销由使用者权衡.
  • 缓解手段是按 agent 收紧沙箱 (如只读), 而不是提供隔离副本.

pi-subagents 机制与纪律, 全都要

  • 机制面: 工作流里 worktree: true 给每个写子代理独立工作区, 产出 patch + handoff 清单回收.
  • 纪律面同样写成明文: 「Keep one writer」, 写完后用 fresh-context 的独立 reviewer 复核, 由父会话综合 — 文档把这套称为安全关键准则.

3.4 插件独自开辟的战场: 信任工程

商业产品默认信任编排的结果; pi-subagents 把「该不该信, 信到什么程度」做成了产品功能.

pi-subagents 验收, 对抗, 边界 — 全部摆上桌面

  • 验收分级: 每个子代理结果可要求 attested → checked → verified 的证据等级, 还可强制「独立复核」— 写者的活儿必须由另一个干净上下文的 reviewer 签字.
  • 对抗性二审: 可选 watchdog 盯着改动挑刺, 并推荐用互补模型 (别家厂商的强模型) 做二审 — 把「模型异构」当安全特性, 这是单厂商商业产品结构上给不了的.
  • 边界显式化: 子代理默认不是编排者, 不许再 spawn; 递归深度守卫默认两层; 追加 spawn 配额需要人明确确认.
  • 双向通信: 子代理遇到决策点可通过 contact_supervisor 反问父会话 (需要决策 / 请求访谈 / 进度通报), 而不是猜着往下写.
why it matters 商业产品的信任模型是「信任平台, 平台信任模型」; 这个插件的信任模型是「默认不信任, 用流程换信任」. 这不是功能多少的差异, 是对「agent 会怎么犯错」的不同假设.

4取舍: 三家各赌了什么

本节目标: 把分歧收拢成三种产品哲学, 看清各自的代价.

Claude Code 赌「专才会复利」

相信团队会反复需要同一种专家: 审查者, 探索者, 数据库守门人. 于是定义可沉淀 (版本控制, plugin 分发), 行为可积累 (跨会话 memory), 委派可自动化.

代价: 概念面大 — 五层作用域, 十几个字段; 自动委派引入不确定性, 模型可能误判路由.

Codex 赌「简单即可靠」

相信分工的时机是资源决策, 该由人 (或仓库里的书面指令) 显式做出. 运行体验做到极致: 线程可见, 可干预, 可收尾, 编排全托管.

代价: 触发负担在用户 — 不主动要求就没有并行; 专精配置的沉淀弱, 自定义格式官方明说还会变.

pi-subagents 赌「控制面值得暴露」

相信用户想要的是旋钮: 验收等级, 对抗审查, 异构模型, 递归守卫, spawn 配额 — 商业产品替你收起来的复杂度, 它全部摆上台面, 连编排都给你一段 JS 直接写.

代价: 概念最多, 学习曲线最陡; 价值依赖使用者的纪律; 且绑定 pi 生态, 受众天然小.

so what 这不是对错题, 是三种用户画像: 要团队资产沉淀的选 Claude Code; 要省心显式驱动的选 Codex; 要把每个环节都捏在自己手里 (甚至想用别家模型做二审) 的, pi-subagents 这种社区插件反而最合身. 商业产品为规模优化, 插件为控制欲优化.

模型与成本路由

Claude Code 子代理默认继承主会话模型, 可按 agent 固定为 sonnet/opus/haiku; 官方卖点之一是「把任务路由到更快更便宜的 Haiku 以控成本」. 推理 effort 也可按 agent 覆盖.

Codex 不显式指定时, 由 Codex 按任务自动平衡智能/速度/价格; 也可在 agent 文件里钉死 model 与 model_reasoning_effort (low → ultra).

pi-subagents 模型无关: 按角色覆盖模型, fallbackModels 支持跨厂商顺序兜底 (配额/超时自动换), thinking 档位可调; watchdog 甚至会推荐一个「互补模型」做对抗二审 — 把模型异构当质量手段.

事实出处

Codex — OpenAI 官方文档「Subagents」页 (learn.chatgpt.com/docs/agent-configuration/subagents 镜像), 及 GitHub openai/codex issue #2604.

pi-subagents — github.com/nicobailon/pi-subagents: README, docs/agents.md (自定义 agent 与覆写机制), docs/workflows.md (编排, worktree, supervisor 通信, 递归守卫).
