1. 核心思想: 进程即上下文隔离

示例的全部设计都围绕一个决定: 每个子 agent 是一个独立的 pi 进程. 不试图在主进程内做上下文管理, 而是直接复用 pi 自身的运行时. 主 agent 通过扩展工具 subagent 发起调用, 扩展负责 spawn 子进程, 监听其输出, 再把结果带回主会话.

关键命令行参数 (见 runSingleAgent):

参数作用
--mode json子进程以 JSON 流模式运行, 把事件逐行写到 stdout, 供父进程解析
-p打印输出 (print), 事件流中包含模型消息
--no-session不写会话文件, 无状态一次性运行
--model <name>来自 agent 定义 frontmatter, 例如 Haiku 做侦察, Sonnet 做规划
--tools <list>限制子 agent 可用的工具白名单
--append-system-prompt <file>把 agent 的 system prompt 从临时文件注入 (见 §3)
设计要点 system prompt 通过 临时文件 传递而非命令行参数: 因为 prompt 可能很长, 且含换行与特殊字符. 扩展用 mkdtemp 创建目录, 以 0600 权限写入, 进程结束后在 finally 中删除文件与目录.

2. 子进程协议: JSON 行事件流

父进程 spawn 子进程后, 从 stdout 逐块读取数据, 按换行切分成 JSON 行. 每一行是一个事件. 扩展只关心两类事件:

  • message_end — 模型完成一条消息 (含 usage 统计, stopReason, model 名)
  • tool_result_end — 工具调用完成

缓冲区处理必须处理半行: 数据块可能在行中间断开, 所以用 buffer += chunk, 按 \n 切分, 最后一段留在 buffer 里, 等 close 事件时再处理残余. 实际收到的事件流形如:

{"type":"message_end","message":{"role":"assistant","content":[{"type":"text","text":"## Files Retrieved\n1. ..."}],"usage":{"input":1234,"output":56,"cacheRead":0,"cacheWrite":0,"cost":{"total":0.002},"totalTokens":1290},"model":"claude-haiku-4-5"}}
{"type":"tool_result_end","message":{"role":"tool","toolName":"grep","content":[...]}}
{"type":"message_end","message":{"role":"assistant","content":[...],"stopReason":"end",...}}

对每条 message_end, 扩展累计 turns, 把 usage.input / output / cacheRead / cacheWrite / cost / totalTokens 累加进结果对象, 并记录 model 名和 stopReason. 这就是后来 TUI 里 3 turns ↑1.2k ↓56 $0.002 ctx:1290 那行统计的来源.

细节 stopReason === "error" 表示 LLM 层错误, "aborted" 表示用户 Ctrl+C. 此时 isFailedResult 判定失败, 错误信息从 errorMessage / stderr / 最后一条输出中选取回传.

3. Agent 定义与发现

Agent 是带 YAML frontmatter 的 Markdown 文件, 正文就是 system prompt. agents.ts 里的 discoverAgents 在每次工具调用时 重新扫描 目录 (README 明确说: 允许会话中途编辑 agent 定义). 

---
name: scout
description: Fast codebase recon that returns compressed context for handoff
tools: read, grep, find, ls, bash
model: claude-haiku-4-5
---

You are a scout. Quickly investigate a codebase and return structured findings
that another agent can use without re-reading everything.

Your output will be passed to an agent who has NOT seen the files you explored.
...

发现逻辑有三层规则:

  1. 扫描两个来源: 用户级 ~/.pi/agent/agents/ 与项目级 .pi/agents/ (从 cwd 向上逐级找最近的 .pi 目录)
  2. 按 scope 过滤: 默认 user; both 时同名项目 agent 覆盖用户 agent (Map 后写胜出)
  3. 缺失字段直接跳过: 没有 name 或 description 的文件不视为 agent

工具白名单解析自 tools 逗号分隔串, 传给子进程的 --tools; 模型同理传给 --model. worker 不写 tools, 因此拥有全部默认工具.

安全模型 项目级 agent 是仓库控制的 prompt, 可以指示模型读文件/跑命令. 因此默认只加载用户级 agent; 只有显式传 agentScope: "both" 或 "project" 才加载项目级. 交互模式下 (检测 ctx.hasUI), 请求项目级 agent 前会弹确认框, 列出 agent 名与来源目录.

4. 三种执行模式

工具的 JSON Schema 参数 (用 TypeBox 定义) 保证三种模式互斥: 同时给出 agent+task, tasks, chain 中的多个即报错.

Single

{ agent, task }

一次调用, 一个进程. 结果直接返回, onUpdate 实时推流.

Parallel

{ tasks: [...] }

最多 8 个任务, 4 并发 (MAX_CONCURRENCY). 每个任务流式更新自己的槽位.

Chain

{ chain: [...] }

顺序执行, 上一步最终输出替换下一步任务里的 {previous} 占位符. 任一步失败即停止.

Chain 的 {previous} 机制

最简单也最关键的编排原语: step.task.replace(/\{previous\}/g, previousOutput). previousOutput 是前一步消息里 最后一条 assistant 文本 (getFinalOutput 从后往前找). 失败时返回 Chain stopped at step N (agent): 错误信息 并标记 isError: true.

Parallel 的并发限流

mapWithConcurrencyLimit 是个经典 worker 池: 固定 limit 个并发 worker, 用共享计数器 nextIndex++ 取任务, 结果按原索引写入数组. 并发调用各任务前先填充 exitCode: -1 的占位结果, 这样 TUI 可以立刻显示所有任务的 ⏳ 状态. 

const workers = new Array(limit).fill(null).map(async () => {
  while (true) {
    const current = nextIndex++;          // 原子取下一个任务
    if (current >= items.length) return;  // 任务耗尽
    results[current] = await fn(items[current], current);
  }
});
await Promise.all(workers);
输出上限 并行模式回传给主模型的文本每个任务截断到 50 KB (PER_TASK_OUTPUT_CAP), 按 UTF-8 字节数计算, 截断时逐字节回退保证不切坏多字节字符, 并注明省略了多少字节; 完整结果保留在工具 details 里.

5. TUI 渲染与用量统计

扩展实现了 renderCall (调用时) 与 renderResult (结果时) 两个渲染器. 调用时只显示一行摘要; 结果时根据 expanded 标志 (Ctrl+O) 切换两种视图:

折叠视图 (默认)展开视图 (Ctrl+O)
任务文本不显示完整显示
工具调用最后 10 条, 单行格式化全部, 逐条
最终输出前 3 行预览Markdown 渲染 (Markdown 组件)
用量一行汇总逐 agent + Total 合计

工具调用格式化为模拟内置工具的样式, 路径缩短为 ~, 命令截断到 60 字符: 

✓ scout (user)
  $ grep -rn "auth" src/ ...
  read ~/project/src/auth.ts:1-40
  3 turns ↑1.2k ↓56 R0 W0 $0.0023 ctx:1290 claude-haiku-4-5

流式更新 (streaming) 贯穿所有模式: onUpdate 回调在每个 message_end / tool_result_end 触发, parallel 模式用一个共享数组让每个任务独立更新自己的槽位, 渲染器据此实时显示 2/3 done, 1 running.

用量统计的另一个作用: formatUsageStats 用 1k/1M 缩写, 成本精确到 4 位小数 — 这给了用户可审计的每步成本, 是链式工作流落地时最实用的反馈.

6. 工作流: prompt 模板编排

Agent 是能力单元 (侦察/规划/实现/审查), 而 prompts/ 里的模板是 流程剧本: 它们不写代码, 只指导主模型如何用 subagent 工具按序组合 agent. 模板里的 $@ 会被用户输入替换.

四个示例 agent 展示了角色分工的价值:

Agent模型工具产出约定
scoutHaiku (快, 便宜)read, grep, find, ls, bashFiles Retrieved (带行号) / Key Code / Architecture / Start Here
plannerSonnetread, grep, find, lsGoal / Plan / Files to Modify / Risks, 禁止改动
workerSonnet全部Completed / Files Changed / Notes, 交接给 reviewer 时给路径清单
reviewerSonnetread, grep, find, ls, bashFiles Reviewed / Critical / Warnings / Suggestions, bash 只读
值得注意 scout 的 prompt 专门写了 "Your output will be passed to an agent who has NOT seen the files you explored" — 这正是链式交接的关键: 输出必须自包含, 下游 agent 无法回看上游的上下文.

7. 边界与安全模型

示例也明确列出自己的局限, 是值得模仿的诚实做法:

  • 并行输出回传上限 50 KB/任务, 折叠视图只显示最后 10 条
  • 每 8 个并行任务 / 4 并发封顶
  • agent 每次调用重新发现, 意味着可以热编辑

失败处理是完整的:

情形行为
退出码 ≠ 0返回错误, 附带 stderr/输出
stopReason: "error"透传 LLM 错误消息
用户 Ctrl+CSIGTERM 先给子进程, 5 秒后仍不退出则 SIGKILL, 全程经 AbortSignal 传播
chain 中途失败停止并报告第几步哪个 agent 失败
未知 agent 名退出码 1, 列出可用 agent

最后回看整体: 这个示例没有发明任何新的 agent 运行时, 它做的是 管道工 的工作 — spawn 进程, 解析事件流, 按模板编排, 渲染进度. 所有智能都来自 pi 自身和精心撰写的 prompt. 它证明了扩展生态最有效的位置: 连接与编排, 而非重复实现.

示例路径: examples/extensions/subagent/ — index.ts (~700 行), agents.ts, agents/ (4 个), prompts/ (3 个). 安装方式为符号链接到 ~/.pi/agent/{extensions,agents,prompts}.
